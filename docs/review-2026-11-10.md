## 3. 问题清单

### R1｜HIGH / P1｜HUD 缓存绑定缺少实际请求 workspace

置信度：高。静态调用链确认；追加纯内存验证显示，相同 JWT subject、不同 providerSpecificData.accountId 的两个样本，accountIdentity 完全相同（输出 different_workspace_same_identity true）。完整 worker 的跨 workspace 失败继承尚未端到端复现。

证据：[worker:91](../Sources/TokenHUD/mjs/ref-usage-provider.mjs#L91)、[身份提取:144](../Sources/TokenHUD/mjs/source-readers.mjs#L144)、[GPT 格式映射:44](../Sources/TokenHUD/providers/gpt/manifest.json#L44)。

worker 使用 accountIdentity 或 token 摘要建立 binding；身份提取未包含 `providerSpecificData.accountId` / 顶层 `account_id`，但 GPT 格式将这些字段映射成实际 `chatgpt-account-id` 请求头。9router 同一用户/JWT subject 切换 workspace 时，实际请求租户变化，binding 可能不变。若新 workspace 请求失败，或请求期间发生切换，旧 workspace 的成功额度仍可能被保留。

影响：违反“只有同账号身份绑定才能继承旧快照”，用户看到另一 workspace 的额度。

建议：将解析后的有效 workspace/request account 身份纳入 binding；同步检查来源 identityAccount 与 Swift 身份规则。增加同 subject、不同 workspace 的失败继承和请求中切换回归。

### R2｜MEDIUM / P2｜cc-switch 读取遗漏复合主键条件

置信度：高。

证据：[Node:458](../Sources/TokenHUD/mjs/source-readers.mjs#L458)、[Swift:55](../Sources/TokenHUD/ImportedSource.swift#L55)、[已有 Swift fixture:101](../Tests/TokenHUDTests/SourceReferenceTests.swift#L101)。

Node 仅按 id 查询，随后要求唯一；Swift 正确按 id + app_type 查询。数据库中 claude/codex 具有同 id 时，B 能查询而 C 报来源缺失。Node fixture 使用单列主键，未覆盖真实复合主键情形。追加离线复现使用 PRIMARY KEY(id, app_type) 创建同 id 双记录，调用实际 readReference 后得到 source-missing；未访问真实账号或网络。

建议：SQL 同时约束 app_type，并使用复合主键及同 id 跨类型数据测试。

### R3｜MEDIUM / P2｜死锁并发回收可能删除新 worker 的锁

置信度：中高；静态竞争时序成立，未做确定性并发复现。

证据：[锁回收:29](../Sources/TokenHUD/mjs/ref-usage-provider.mjs#L29)、[释放:201](../Sources/TokenHUD/mjs/ref-usage-provider.mjs#L201)。

两个 worker 都读到已死亡 owner 后，各自无条件删除锁目录。第一个建立的新锁可能被第二个根据旧观察删除；若两者都在尝试时间写入前通过 TTL 检查，就会并发请求。finally 同样未核验 owner。

建议：使用能序列化回收的锁机制，并以 owner token/inode 校验释放归属。新增“死锁 + 多 worker 同时恢复”组合测试；现有无旧锁并发和单 worker 恢复不能证明该组合安全。

### R4｜MEDIUM / P2｜系统时钟回拨会延长 HUD 查询节流

置信度：高。

证据：[渲染 TTL:222](../Sources/TokenHUD/mjs/statusline.mjs#L222)、[worker TTL:19](../Sources/TokenHUD/mjs/hud-runtime.mjs#L19)。

渲染器只判断 now - timestamp < 60000，未拒绝未来时间；worker 的 helper 却拒绝未来时间。查询后系统时间回拨一小时，渲染器可能一小时不启动 worker，并把旧额度当新鲜值，worker 中正确判断没有执行机会。

建议：渲染与 worker 共用有限数、非未来时间校验；成功新鲜度同样处理未来时间。增加未来缓存时间戳测试。

### R5｜MEDIUM / P2｜计划实际调用模型与基础编辑页展示不一致

置信度：高。

证据：[执行优先级:89](../Sources/TokenHUD/RefreshTrigger.swift#L89)、[编辑页说明:247](../Sources/TokenHUD/ui/SettingsCenter/DraftFormView.swift#L247)、[保存:981](../Sources/TokenHUD/ui/SettingsCenter/SettingsModel.swift#L981)。

基础编辑页承诺调度使用当前选定模型，保存写入 testModel；执行器却优先 windowModelOverride 和 manifest.windowTrigger.model。用户选择非默认模型并启用计划，实际可能执行模板默认模型；曾保存本地 override 后再改基础模型，也可能继续执行旧 override。

影响：发送请求的模型与用户确认的模型不一致，涉及套餐和消耗预期。

建议：统一有效计划模型解析及两个编辑入口，明确显示最终模型；为旧计划提供明确迁移规则。补“编辑保存 → 实际请求 body”回归，不能只测试执行器自身优先级。

### R6｜MEDIUM / P2｜有效本地计划被误判为账号异常

置信度：高。

证据：[健康判断:85](../Sources/TokenHUD/ui/SettingsCenter/AccountHealth.swift#L85)、[详情状态:327](../Sources/TokenHUD/ui/SettingsCenter/ConfigTabView.swift#L327)、[计划保存:1145](../Sources/TokenHUD/ui/SettingsCenter/SettingsModel.swift#L1145)。

基础/来源 testModel 为空，但本地 windowModelOverride 有效时，保存与执行链接受该计划；健康判断仍只检查 testModel。账号因此被标记“调用计划未配置模型”，并可能从默认“启用且正常”侧栏隐藏，详情也提示先配置调用。

建议：健康、详情、保存和执行复用同一有效计划模型解析。补基础模型为空、本地计划模型非空的测试；现有 fixture 固定有 source-model，漏掉该分支。

### R7｜MEDIUM / P2｜待导出提示漏标改名，且重启丢失

置信度：高。重启丢失已在设计文档中列为实现边界；改名漏标是额外缺口。

证据：[改名:762](../Sources/TokenHUD/ui/SettingsCenter/SettingsModel.swift#L762)、[内存标记:223](../Sources/TokenHUD/DataEngine.swift#L223)、[标记函数:592](../Sources/TokenHUD/DataEngine.swift#L592)。

导入账号改本地名称后只保存并 reloadRegistry，未标记待导出；已有待导出状态在重启时恢复 false。C 继续使用旧配置符合架构，但 UI 不提示尚未写入，不满足契约要求。

建议：持久化 dirty 状态或比较已导出配置指纹，覆盖改名等全部导出相关动作，只在完整成功导出后清除；补改名和重启测试。

### R8｜MEDIUM / P2｜导出不能无损保留第三方 HUD 条目

置信度：高，固定 Codable 结构的读写链明确。

证据：[固定结构解码:78](../Sources/TokenHUD/HUDSync.swift#L78)、[全部条目解码:208](../Sources/TokenHUD/HUDSync.swift#L208)、[全量编码:222](../Sources/TokenHUD/HUDSync.swift#L222)。

已有条目先解码成 EnvsEntry，再统一编码。第三方自定义字段和未知元数据会丢失；第三方同名字段采用其他结构时还可能使整个导出失败。保留第三方 key、label 和 cache 不等于保留其完整配置。

建议：未受管条目保留原始 JSON，只替换确定归 QuotaNest 管理的条目；补未知顶层/嵌套字段往返测试。目前第三方测试也使用 EnvsEntry 创建 fixture，无法发现未知字段丢失。

### R9｜MEDIUM / P2｜Node 回归存在已确认失败

证据：[断言:81](../scripts/test-catalog-coding-providers.mjs#L81)、[实际日志:391](../.build/review-20261110-node.log#L391)。

`node --test scripts/test-*.mjs` 退出码 1。TAP 汇总：285 项，284 通过、1 失败、0 跳过。失败文件为 test-catalog-coding-providers，具体断言要求 quotaAuthModes 严格等于 `[apikey]`，实际是 `[apikey, auth]`。

追加核对已定位为 [zai-coding 类型声明:15](../Sources/TokenHUD/providers/zai-coding/manifest.json#L15)：同时声明 apikey/auth，并有 refresh.key 的只读 credentialSource 及 Auth 调用端点。旧测试把所有 codingProviders 统一限制为仅 apikey，未反映此声明。建议按供应商能力维护预期，并补 Z.ai Auth 的正反向场景；不要为变绿删除认证能力校验。该文件在断言处提前退出，后续场景没有执行；TAP 通过数不等于全部脚本内部自定义场景总数。
